# ADR 0021: Native backend (Cranelift) and runtime (Phase 3)

- **Status:** Accepted (provisional; revisited at the end of Phase 3)
- **Date:** 2026-10-29
- **Deciders:** lead architect
- **Related:** [ADR 0009](0009-backend-strategy.md), [ADR 0012](0012-platform-tiers.md),
  [ADR 0020](0020-mir-and-ownership-checking.md), [ADR 0017](0017-rust-as-the-base.md)

## Context

ADR 0009 makes Cranelift the first native backend, consuming MIR, differentially tested
against the interpreter. Phase 3's exit criteria are native binaries on every Tier 1
target, differential tests that match the interpreter, and no leaks or use-after-free
under sanitizers. This ADR fixes how MIR becomes machine code: representation of values,
the calling convention, monomorphization, drops, panics, the runtime library, and how
programs are run and linked.

## Decision

### 1. Two ways to run native code

- **JIT** (`loom run`, once the backend covers the program): `cranelift-jit` compiles the
  monomorphized program into the `loom` process. The runtime is part of the `loom`
  binary, so its functions are registered with the JIT by name and nothing is linked.
- **AOT** (`loom build -o <exe>`): `cranelift-object` writes an object file, and the
  system linker (`cc` on Linux and macOS, `link.exe` through the MSVC environment on
  Windows) links it with the runtime static library `libloom_runtime.a` /
  `loom_runtime.lib`, shipped next to the `loom` binary (`../lib/` relative to it, or
  `LOOM_RUNTIME_LIB`).
- `loom run --interp` selects the reference interpreter. Until the backend covers every
  construct, `loom run` falls back to the interpreter for programs it cannot compile,
  and says so with `--verbose`.

### 2. Monomorphization

Codegen starts from `main` (or the test functions) and compiles each reachable
`(MIR body, concrete substitution)` once. Trait calls are resolved for the concrete type
with the trait solver: an impl method, a provided method, or **glue** generated by the
backend for built-in and derived impls (`Eq`, `Ord`, `Clone`, `Hash`, `Copy`, `Default`)
of primitives, tuples, structs and enums. Symbols are `loom_<package>_<path>_<hash>`
where the hash covers the substitution.

### 3. Value representation

| Loom type | Representation |
|---|---|
| integers, `Char` (u32), `Bool` (u8), floats | the Cranelift scalar of that width |
| `Unit`, `Never` | nothing (size 0) |
| `ref T`, `mut ref T` | a pointer |
| `String`, `Bytes`, `Array[T]`, `Map[K, V]` | a pointer to a runtime-owned object |
| tuples, structs | C layout of the fields in declaration order |
| enums | a `u32` tag followed by the largest payload, C-aligned |
| `Fn(…)` values | `{code pointer, environment pointer}` (environment on the heap) |
| `dyn Trait` | `{data pointer (heap), vtable pointer}` |

Every MIR local lives in a stack slot of its layout; aggregates are copied with
`memcpy`. This is simple rather than fast; Phase 7 (LLVM) and MIR optimizations improve
it. The calling convention, as implemented:

- **Functions:** a result pointer first (every result, scalar or not, is written through
  it into a fresh slot of the caller), then each argument: a scalar by value, an
  aggregate as a pointer to a caller-owned copy that the callee owns, nothing for a
  zero-size value. Borrowed parameters are `ref` locals in MIR and so are pointers.
- **Closures:** `(result, environment, arguments…)`, where every argument is borrowed
  (a pointer), as MIR passes arguments to callable values. Runtime callbacks
  (`sort_by`, `update`) use the same convention. The environment is heap-allocated:
  two words of header (its drop and clone functions), then the captures in C layout.
- **Functions and constructors used as values** get a shim with the closure convention
  and a null environment. A shim deep-copies arguments that the target takes `own`.
- **`dyn` vtables:** drop glue, size, alignment, clone glue, then the trait's methods
  that take a receiver, ordered by name. A `dyn` method call passes the data pointer as
  the receiver.
- **Value semantics of copies:** a MIR `Copy` of a place whose type owns resources
  (possible where the interpreter's copy-on-write values made it free) is a deep copy
  through clone glue, so a value is never owned twice.

### 4. Runtime (`runtime/`, crate `loom_runtime`)

A Rust library with an `extern "C"` API, built both as an `rlib` (for the JIT, linked
into `loom`) and as a `staticlib` (for AOT). It provides: the heap objects behind
`String`, `Bytes`, `Array` and `Map` (insertion-ordered, hashing through per-type glue),
the core intrinsics of `docs/internals/intrinsics.md`, buffered standard output, number
formatting (spec §7.12), and panics. Generic collections receive a **type descriptor**
for their element type: size, alignment and glue functions (drop, clone, eq, compare,
hash, debug text) generated by the backend. The runtime is the place where `unsafe` is
allowed (ADR 0005 §7), with a `// SAFETY:` comment on every block, and it is tested
under Miri and AddressSanitizer in CI.

### 5. Checks and panics

Integer overflow (Cranelift's `*_overflow` instructions), division by zero, shift
amounts, array bounds and map keys are checked inline and call `loom_panic` with the
message and source position. A panic flushes standard output, writes
`panicked at <file>:<line>:<col>: <message>` to standard error and exits with status
101. Unwinding (and drops during a panic) arrive with the Phase 4 runtime (ADR 0020 §5
rule 4); until then a panicking program does not run drops, and the interpreter skips
them on panic too so that the two agree.

### 6. Drops

The backend implements MIR `Drop` with **drop flags**: every local whose type owns
resources gets a flag, set when it is initialized and cleared when it is moved;
`StorageLive`/`StorageDead` clear it. Every field path that MIR moves, drops or assigns
separately (`move p.first`, `drop(p.first)`, `p.first = …`) gets its own flag, so a
partially moved value drops exactly its remaining fields: a drop of a local walks its
type and skips the paths whose flags are clear. As in Rust's MIR, an assignment never
drops the old value; MIR emits an explicit `Drop` before assigning to an initialized
place. The MIR builder schedules drops for statement temporaries, including on early
exits (`return`, `?`, `break`, `next`) and in expression bodies. `Drop` of a value whose
type implements `Drop` (once the core trait exists) calls `drop`, then drops its fields;
runtime objects free their memory and drop their elements through the type descriptor.

### 7. Differential testing

`cargo xtask differential` runs every example and every accept case of the conformance
suite with the interpreter and with the native backend and requires identical standard
output and exit status. It is part of `cargo xtask ci` from the moment the backend
compiles the examples. The runtime counts its live objects; with `LOOM_LEAK_CHECK=1` a
program that ends with live objects reports them, and the differential test fails on
such a report. `--aot` also builds and runs each program with `loom build`, and
`--valgrind` runs those executables under Valgrind (Linux CI).

### 8. The JIT trust boundary

The code generator crate may not contain `unsafe` code (only `runtime/` may, CLAUDE.md).
Calling the JIT-compiled entry point needs one cast from an address to a function
pointer; it lives in the runtime as `run_jit_entry`, a documented trust boundary whose
only caller is the JIT.

### 9. Dependencies

`cranelift-codegen`, `cranelift-frontend`, `cranelift-module`, `cranelift-jit`,
`cranelift-object` and `target-lexicon`, version-pinned together, used only by
`loom_codegen_cranelift`, each with a row in `docs/dependencies.md`. Exit plan: the
backend sits behind MIR (ADR 0009 rule 2); LLVM (Phase 7) is the second backend, and the
interpreter remains the oracle.

## What Rust does

`rustc_codegen_cranelift` is the model: Cranelift from monomorphized MIR, aggregates in
stack slots, glue for drops, a JIT mode for quick runs. Rust's drop elaboration with drop
flags and move paths is the model for §6. Rust passes large aggregates indirectly and
returns them through a hidden pointer, as §3 does. Loom's collections live in a runtime
written in Rust with per-type descriptors instead of being monomorphized Loom code over
raw pointers, because Loom has no raw pointers in safe code yet; the descriptors are the
same idea as Rust's vtables.

## Alternatives considered

- **Only AOT:** every `loom run` would need a linker on the user's machine; JIT removes
  that for the common case.
- **Collections written in Loom over raw memory:** the long-term shape (as Rust's `std`),
  but it needs `unsafe` Loom and pointer intrinsics that are not designed yet.
- **Rust-emit:** deferred by the owner (ADR 0009).
- **Unwinding now:** Cranelift supports it, but scopes and tasks (Phase 4) define where a
  panic stops; doing it twice is waste.

## Consequences

- The `loom` binary grows by the size of Cranelift (a few MB).
- Releases must ship the runtime static library with the binary for `loom build`.
- Programs whose behavior depends on drops during a panic differ from the spec until
  Phase 4; `docs/STATUS.md` says so.

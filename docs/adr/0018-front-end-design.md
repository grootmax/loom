# ADR 0018: Front-end design (Phase 1)

- **Status:** Accepted (provisional — revisited at the end of Phase 1)
- **Date:** 2026-10-28
- **Deciders:** lead architect
- **Related:** [ADR 0008](0008-compiler-architecture.md), [ADR 0003](0003-syntax-philosophy.md),
  [spec §2, Appendix C](../../spec/loom-spec.md), [grammar.ebnf](../../spec/grammar.ebnf)

## Context

Phase 1 builds the front end: lexer, parser, lossless CST, typed AST views, the
diagnostics engine and `loom fmt`. ADR 0008 fixes the architecture: a hand-written parser,
an in-house green/red tree, and in-house diagnostics. This ADR records the remaining
decisions an implementer needs: data types, crate boundaries, error codes, how the parser
settles cases the grammar leaves open, and how we test and fuzz all of it. It also moves
the date on which salsa arrives.

## Decision

### 1. Crates and dependency order

```
loom_span ─► loom_diagnostics ─┬─► loom_lexer ──┐
loom_unicode ──────────────────┤                ├─► loom_parser ─► loom_ast ─► loom_fmt
loom_syntax (kinds + tree) ────┴────────────────┘                     └─► loom_driver ─► loom_cli
```

- `loom_syntax` owns `SyntaxKind`, which lists every token and node kind, plus the
  green/red tree. The lexer depends on it for token kinds, and the parser for both.
- `loom_unicode` (new) holds generated Unicode tables: `XID_Start`, `XID_Continue`,
  `White_Space`, and later NFC and UTS #39 confusables. The tables are generated by
  `cargo xtask gen-unicode` from the Unicode Character Database, version **17.0.0**. The
  data is licensed Unicode-3.0, which `deny.toml` already allows. This adds no crate
  dependency.
- `loom_snapshot` (new, used only as a dev-dependency) is an in-house snapshot-testing
  helper (§8). It replaces `insta` and keeps the dependency count at zero.

### 2. Spans and positions (`loom_span`)

- `TextSize` is a `u32` byte offset, and `TextRange` is a half-open `[start, end)` pair of
  them. Source files are therefore limited to 4 GiB. A larger file is rejected when it is
  loaded.
- A `FileId` (`u32`) indexes a `SourceMap`. A `SourceFile` holds its name, its text and a
  line index. A `Span` is a `FileId` plus a `TextRange`.
- **Positions shown to people and in conformance `.diag` files** are a 1-based line and a
  1-based column. The column counts Unicode scalar values from the start of the line, so a
  tab counts as one column. Tools that speak LSP convert to UTF-16 at their own boundary.

### 3. Diagnostics (`loom_diagnostics`)

- A `Diagnostic` has a severity (`Error`, `Warning`), an optional stable `Code`, a
  message, one primary label and any number of secondary labels (each a `Span` with
  optional text), notes, help lines, and suggestions. A `Suggestion` is a message, a list
  of text edits, and an `Applicability`: `MachineApplicable`, `MaybeIncorrect`, or
  `HasPlaceholders`.
- **Error codes** are `E` plus four digits. The ranges are E0001–E0099 for lexical errors,
  E0100–E0199 for syntax errors, E0200–E0299 for names and modules, E0300–E0499 for types
  and traits, E0500–E0599 for ownership, and E0600–E0699 for concurrency. Each range is
  reserved for its phase. A code is never reused, even after the error it named is removed.
- **Warnings are named lints** in `snake_case`, such as `dangling_doc_comment`, not numbered
  codes. Lints can be allowed or denied by name, as in Rust. Phase 6 adds the lint
  configuration.
- The registry is **spec Appendix C**, which is normative for conformance.
  `loom_diagnostics::codes` mirrors it, and a test keeps the two identical. Each code has a
  long explanation in `compiler/loom_diagnostics/explanations/EXXXX.md`, shown by
  `loom explain EXXXX`.
- The renderer is in-house and resembles rustc's: a header line, a `-->` location, a source
  snippet with `^^^` (primary) and `---` (secondary) underlines, then `= note:` and
  `= help:` lines. Color is opt-in, and tests render without it.

### 4. Lexer contract (`loom_lexer`)

- `lex(text: &str, file: FileId) -> Lexed`, where `Lexed` holds the full token sequence
  (kind and length) *including trivia*, plus the diagnostics. Concatenating the tokens
  reproduces the input byte for byte. The lexer never fails and never panics. Bad input
  becomes an `ERROR_TOKEN` or a best-effort token, together with a diagnostic.
- A line terminator is either a significant `NEWLINE` token or, when §2.3 rule 1 suppresses
  it, a `LINE_BREAK` trivia token.
- Interpolated strings are a token sequence: `STRING_START`, `STRING_FRAGMENT`,
  `INTERP_START`, the tokens of the expression, `INTERP_END`, and `STRING_END`. The lexer
  keeps a mode stack so that strings nest inside interpolations to any depth.
- Reserved words are lexed as `IDENT`, with diagnostic E0009, so parsing continues as if
  they were identifiers. The contextual keyword `default` is an `IDENT`.
- Invalid UTF-8 (E0001) is reported once per file, at the first bad byte. The driver then
  lexes the lossy conversion (U+FFFD replacement) so that the tools keep working.

### 5. Lossless CST (`loom_syntax`)

- **Green tree:** immutable, position-independent, and `Arc`-shared (it is `Send + Sync`
  for the LSP). A `GreenToken` holds a kind and its text. A `GreenNode` holds a kind, a
  cached text length and its children.
- **Red tree:** `SyntaxNode` and `SyntaxToken` are cheap `Rc` cursors that carry a parent
  pointer and an absolute offset. They are created on demand and are not `Send`.
- `GreenNodeBuilder` supports `start_node`, `token`, `finish_node`, and checkpoints, which
  let a node be wrapped retroactively for Pratt parsing.
- **Losslessness is a tested property:** for every input, valid or not, the tree's text
  equals the source.

### 6. Parser (`loom_parser`)

- **Event-based**, as in rust-analyzer. The grammar code emits `Start`/`Finish`/`Token`/
  `Error` events over the non-trivia tokens. A sink then builds the green tree and attaches
  trivia. Comments and doc comments directly before an item are attached inside the item's
  node. Other trivia goes to the enclosing node.
- Recursive descent for items and statements. A Pratt loop for expressions, with binding
  powers taken from spec §7.5.
- **Newline contexts:** the parser keeps a stack of "newlines significant / ignored". In
  bracketed contexts (§2.3 rule 2) the peek functions skip `NEWLINE`. When the parser
  consumes the next token, it first adds any skipped `NEWLINE`s to the tree, so no text is
  lost. Block bodies push "significant".
- **Recovery:** `expect` reports a missing token and continues without consuming. An
  unexpected token is wrapped in an `ERROR` node, unless it is in the current recovery set.
  Statement-level recovery skips to the next `NEWLINE` or to a block terminator
  (`end`, `else`, `elsif`, `in`, `when`, `}`). **Indentation is a recovery hint only:** an
  item keyword (`def`, `struct`, `enum`, `trait`, `impl`, `module`) in column 1 inside a
  nested block body closes that body, and the parser reports E0102 "missing `end`" at the
  opener. Indentation never changes the meaning of a valid program.
- **Nesting limit:** nesting deeper than 256 levels reports E0112 and stops descending.
  This keeps the parser from overflowing the stack, which matters for fuzzing.
- The parser must not panic on any input. This is a fuzzed invariant (§9).

### 7. Disambiguation rules (now spec text)

The grammar alone leaves several cases open. These rules are written into the spec
sections shown:

1. **Closure parameters** (§7.9): a block parameter is a `pattern_atom`, so a top-level
   or-pattern must be parenthesized: `{ |(A | B)| … }`. This is what lets `|` close the
   parameter list.
2. **Trailing blocks** (§7.3): `{` or `do` is a trailing block of the expression before it
   only when it is on the same line. A `{` that starts an operand is a closure if the next
   token is `|`, and a map literal otherwise.
3. **Command calls** (§4.4): a statement is a command call when it starts with an `IDENT`
   that is followed by whitespace (not a line break) and then by a token that can start a
   command argument: a literal, `STRING_START`, `IDENT`, `AT_IDENT`, `self`, `Self`, `not`
   or a label `IDENT :`. `not` is included because it has no binary reading, so
   `puts not done` is unambiguous; `-`, `[`, `(` and `{` are excluded because they do.
4. **Bindings and assignments** (§4.1–4.2): the parser produces `BIND_STMT` for
   `var x …`, `x: T = …` and plain `x = …`, and `ASSIGN_STMT` for compound operators and
   for any place other than a lone identifier. Name resolution decides whether a plain
   `x = …` is a new binding or an assignment to an existing `var`.
5. **`select` arms** (§11.3): `when P = e` is a receive arm with a pattern if a `=` appears
   at bracket depth 0 before `then` or the end of the line. Otherwise the arm is `when e`.

### 8. Testing

- `loom_snapshot` provides `assert_snapshot!(name, actual)`. Snapshots live next to the
  test in `tests/snapshots/<name>.snap`. `LOOM_BLESS=1` rewrites them. A missing snapshot
  fails the test in CI (`CI` is set) and is created locally.
- CST dumps (an indented `KIND@start..end` tree with quoted tokens) are snapshot-tested
  for every grammar rule. Every diagnostic is snapshot-tested through the renderer.
- `cargo xtask conformance` runs `spec/conformance/`. In Phase 1 it checks `.diag` files
  whose codes are lexical or syntax codes (E0001–E0199). An accept case (`.stdout`) must
  produce no lexical or syntax diagnostics. Its output is checked once the interpreter
  exists, in Phase 2.
- Properties checked on every example and conformance file: lossless round trip;
  `fmt(fmt(x)) == fmt(x)`; `parse(fmt(x))` has the same structure as `parse(x)`, ignoring
  trivia.

### 9. Fuzzing

An in-house, std-only fuzzer (`tools/loom_fuzz`). It mixes three input sources: byte- and
token-level mutation of a corpus (the examples and conformance files), generation from the
grammar, and splicing. The invariants are: no panic, a lossless round trip, no infinite
loop (each input gets a time budget), and formatter idempotence on input that parses
without errors. The Phase 1 exit criterion, "fuzzed 24 h clean", means **24 CPU-hours
without a failure across the parser targets**. A nightly GitHub Actions workflow runs
4 shards × 6 h. Crashing inputs are minimized and added to the corpus as regression tests.
Coverage-guided fuzzing (cargo-fuzz and libFuzzer) can come later in a separate,
non-workspace `fuzz/` directory if the in-house fuzzer plateaus.

### 10. Formatter (`loom_fmt`)

The style is canonical, with no options: 2-space indentation, a 100-column target, one
blank line at most between statements, and one blank line between items. Comments are
kept. The formatter works on the CST and refuses to format a file that has syntax errors
(exit status 1, diagnostics printed). The full style lives in `docs/reference/style.md`.
`loom fmt --check` exits with status 1 if any file would change.

### 11. salsa arrives in Phase 2, not Phase 1

ADR 0008 §5 adopts salsa "in Phase 1". In Phase 1, each file is lexed and parsed
independently, there are no queries across files, and nothing is worth memoizing. Adding
salsa now would add a dependency with no work to do. We adopt it in Phase 2, together
with name resolution, which brings the first queries that span files. ADR 0008's choice of
salsa and its exit plan are unchanged. Only the date moves.

## What Rust does

rustc has a lossy token stream and AST. The lossless tree lives in a different code base,
rust-analyzer, with its own parser, so the two drift. Loom has one parser and follows
rust-analyzer's design (event-based parsing, green/red trees, typed AST views) with no
second front end. rustc's error codes (`E0308`) and rendering style are the model for
diagnostics. We reserve code ranges per phase, which rustc does not, so that a code's
number hints at the stage that reported it. Rust's warnings are named lints. Ours are too.

## Alternatives considered

- **Lexer emits only significant tokens; the parser re-lexes trivia:** rejected. It
  duplicates work, and losslessness becomes an accident rather than a property.
- **Making newline significance entirely the parser's job:** rejected. The lexical rule
  (§2.3 rule 1) is easy to state about tokens, and doing it in the lexer keeps the
  parser's lookahead small.
- **`insta`, `cargo-fuzz` or `unicode-ident` as dependencies:** each is a good crate, but
  ~200–400 lines of in-house code covers our needs and keeps Phase 1 at zero dependencies.
  We would revisit this if maintaining our version costs more than adopting theirs.
- **salsa in Phase 1, as ADR 0008 planned:** rejected for now (§11).

## Consequences

- The lexer, parser and formatter can all be tested and fuzzed without the driver.
- The spec gains Appendix C (the code registry) and the disambiguation text in §7. Changing
  either now needs an ADR or RFC, like any other spec change.
- Two new workspace crates: `loom_unicode` and `loom_snapshot`.
- Recovery that relies on indentation can be wrong for badly indented, unfinished code.
  It only affects which errors are reported, never what a valid program means.
